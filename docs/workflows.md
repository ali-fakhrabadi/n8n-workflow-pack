# The workflows

All four exports are in [`workflows/`](../workflows). They are generated by
[`scripts/build_workflows.py`](../scripts/build_workflows.py) from one definition and the Code
node sources in [`src/code/`](../src/code), so the logic in the JSON is the logic the unit tests
cover.

## Shared pattern

Each of the three workflows starts with the same six nodes:

| Node | What it does |
|---|---|
| **Webhook** | `POST`, header-token authentication (`X-Webhook-Token`). A wrong or missing token gets `403` from n8n and starts no execution. Answers come from the Respond nodes. |
| **Settings** | Every tunable value in one place (service URLs, time limits, retry attempts). `setup/setup.mjs` fills it from environment variables on import. |
| **Validate …** | Code node. Required fields, formats, size limits. Invalid input goes to **Reject 400** with the reason; nothing else happens. |
| **Claim key** | One atomic PostgreSQL statement on the ledger (see below). Returns a row only for the first delivery of a key, or for a redelivery of a failed one. |
| **First delivery?** | Row returned: **Accept 202** and continue. No row: **Duplicate 200** (`{"duplicate": true}`) and stop. |
| **Accept 202** | The sender gets its answer at once; the rest of the run happens after it. |

and ends with the same two:

| Node | What it does |
|---|---|
| **Record outcome** | Sets the ledger row to its final status (`done`, `rejected`, `expired`, `skipped`) with a small outcome document. Only the execution that holds the claim can finish it. |
| **Post run notice** | A one-line notice to the chat channel (best effort). |

### Retries

Outbound calls that create something (publish a post, append a row, upsert a contact) use a
loop instead of n8n's built-in retry, because the built-in retry also repeats permanent errors:

```
HTTP Request (full response, never throws) → Classify → Switch
     ▲                                                 ├─ ok     → continue
     └──────────── Back off (Wait, wait_s) ◄───────────┤─ retry  (no response, 408, 429, 5xx)
                                                       └─ failed → Fail run (Stop and Error)
```

`Classify` ([`classify_response.js`](../src/code/classify_response.js)) waits exponentially with
full jitter (`retry_base_s × 2^(attempt−1)`, half to full), honours `Retry-After`, caps at 300 s
and gives up after `max_attempts` (4 by default). Other 4xx answers fail at once. Idempotent
calls (chat notices, CRM reads and stage updates, SMTP) use n8n's built-in retry.

Every create call carries the event key as an `Idempotency-Key` header, so an API that
supports it can de-duplicate too. The mocks in the tests deliberately do not: a duplicate run
there shows up as a second post or row.

### Idempotency ledger

[`setup/ledger.sql`](../setup/ledger.sql) creates one table, `idempotency_keys`, keyed by
`(workflow, key)`. The claim:

```sql
INSERT INTO idempotency_keys (workflow, key, status, execution_id)
VALUES ($1, $2, 'processing', $3)
ON CONFLICT (workflow, key) DO UPDATE
   SET status = 'processing', execution_id = EXCLUDED.execution_id,
       attempts = idempotency_keys.attempts + 1, error = NULL, updated_at = now()
 WHERE idempotency_keys.status = 'failed'
    OR (idempotency_keys.status = 'processing'
        AND idempotency_keys.updated_at < now() - make_interval(secs => $4::double precision))
RETURNING workflow, key, attempts;
```

- Ten copies arriving at the same moment: PostgreSQL serialises them on the primary key, one
  gets the row, nine get nothing and answer `200 duplicate`.
- A key that is still running (for example a post waiting for approval) or finished is never
  run again.
- A run that failed was released by the error workflow (`status = 'failed'`), so the sender's
  next delivery of the same event runs again, with `attempts` counting up.
- A claim left in `processing` for longer than `claim_stale_after_s` (n8n crashed mid-run) can
  be taken over. For the two workflows that wait, the wait is added to that limit.

The workflows' database role needs only `SELECT, INSERT, UPDATE` on this table.

### Error workflow

`00 Error handler` is set as the error workflow of the other three. On any failed execution it:

1. reads the failed execution's id, workflow, last node and message (no payload),
2. sets that execution's ledger row to `failed` (so a redelivery can run),
3. posts a `workflow_error` alert to the chat channel with those ids and the event key.

It must be published like the others: n8n 2.x skips an error workflow that has no published
version.

## 01 Social post with human approval

`POST /webhook/social-post-requests`

```json
{"request_id": "post-2026-11-27-01", "channel": "linkedin", "text": "…",
 "media_url": "https://cdn.example.com/a.png", "requested_by": "marketing@example.com"}
```

- **Validation:** `request_id` (1-100 of `A-Z a-z 0-9 . _ : -`), `channel` one of `x` (280),
  `mastodon` (500), `linkedin` (3000), `facebook` (5000), text length in Unicode code points,
  no control characters, `media_url` optional and `https` only.
- **Approval:** `Approval message` builds approve and reject links from the execution's resume
  URL (n8n adds a resume token to it); `Ask for approval` posts them to the chat channel;
  `Wait for decision` waits for the first click or `approval_timeout_s` (48 h by default). A
  later click finds no waiting execution. Anything but `approve` counts as a rejection.
- **Publish:** retry loop around `POST {social_api_url}/v1/posts`.
- **Ends:** `done` (published, with post id and URL), `rejected`, `expired`, or an alert.

## 02 Email to spreadsheet

`POST /webhook/inbound-email`: the JSON your mail provider's inbound webhook posts (map the
field names in `Validate email` if yours differ):

```json
{"message_id": "<abc@mail.example.com>", "from": "Billing <billing@example.com>",
 "subject": "Invoice 1001", "date": "Tue, 24 Nov 2026 09:15:00 +0000", "text": "…", "html": "…"}
```

- **Validation:** Message-ID present (normalised: angle brackets, case and spaces removed, so
  three spellings are one email), sender is an address, text present (HTML-only mail is
  converted), at most 100,000 characters.
- **Extraction** ([`extract_invoice.js`](../src/code/extract_invoice.js)): labelled lines for
  invoice number, PO number, total, currency and due date. Amounts in `1,234.50`, `1.234,50`
  and `12 500,00` form; dates as ISO, `15 Jan 2027`, `January 5, 2027`, or a slash date whose
  day/month order is unambiguous. No model is involved, so the same email always gives the
  same row.
- **Row:** `message_id, received_at, from, vendor, invoice, po, amount, currency, due, status,
  issues`. Complete rows go to the `Invoices` tab, rows with a missing or ambiguous field to
  `Review` with the reason.
- **Append:** retry loop around the Google Sheets `values:append` call. With a real sheet,
  replace the downstream credential by a Google service-account token, or swap the HTTP node
  for n8n's Google Sheets node and keep the loop.

## 03 Lead follow-up sequence

`POST /webhook/lead-submissions`

```json
{"submission_id": "form-8812", "name": "Robin Avery", "email": "robin@example.com",
 "company": "Avery Tools", "message": "…", "consent": true, "source": "pricing-page", "website": ""}
```

- **Validation:** `submission_id`, a plausible email (normalised to lower case), a name,
  `consent === true`, message up to 5,000 characters, and an empty `website` honeypot (bots
  fill it).
- **CRM:** retry loop around `POST {crm_api_url}/v1/contacts:upsert` (found by email or created).
  A contact whose stage is no longer `new` is already in a sequence: the run ends `skipped`.
- **Sequence:** first email at once (SMTP), stage `contacted`, wait `follow_up_delay_s` (3 days
  by default; n8n stores the waiting run), read the contact again: stage `replied` ends the
  sequence, otherwise one follow-up email and stage `follow_up_sent`.
