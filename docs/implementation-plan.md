# Implementation plan

Three import-ready n8n workflows that survive real use, plus the error workflow, the test
harness and CI that prove it. Every number in the README comes from a harness run; nothing is
estimated.

## Scope

| # | Workflow | Trigger | Sinks (mocked in tests) |
|---|---|---|---|
| 01 | Social post with human approval | `POST /webhook/social-post-requests` | chat (approval request, notices), social API |
| 02 | Email to spreadsheet extraction | `POST /webhook/inbound-email` (inbound-parse JSON, as Postmark/Mailgun/SendGrid send it) | spreadsheet API (Google Sheets `values:append` shape) |
| 03 | Lead follow-up sequence | `POST /webhook/lead-submissions` | CRM API, SMTP (Mailpit) |
| 00 | Error handler | Error Trigger of 01-03 | idempotency ledger, chat alert |

Each workflow has:

- **Input validation** in a Code node (tested with `node --test`): required fields, formats,
  size limits, per-channel rules; an invalid event gets `400` with a reason and changes nothing.
- **Authentication** of the webhook (header token credential); a wrong token gets `403` from
  n8n before any node runs.
- **Idempotency** through a ledger table in PostgreSQL: one atomic
  `INSERT ... ON CONFLICT DO UPDATE ... WHERE status = 'failed' RETURNING` claims the event key.
  A repeat of a running or finished event gets `200 {"duplicate": true}` and does nothing, even
  when the copies arrive at the same moment. A failed event is released by the error workflow,
  so a later redelivery runs again instead of being swallowed.
- **Retries** around every outbound call: transient answers (connection error, 429, 5xx) are
  retried with exponential backoff, jitter and `Retry-After`; permanent ones (other 4xx) stop
  at once. Outbound writes carry the idempotency key (`Idempotency-Key` header or key column).
- **An error workflow**: any failure marks the ledger row `failed` and posts an alert with the
  workflow, node, execution id and key, never the payload.

## Architecture

```
sender ──HTTP──> n8n webhook ──> validate ──> claim key (PostgreSQL ledger)
                                   │400          │ duplicate → 200
                                   ▼             ▼ new → 202, then work
                                               outbound calls with retry loop
                                               └─ failure → Stop and Error → error workflow
```

- n8n `2.45.6` (pinned by digest) with PostgreSQL as its database and external task runners
  (`n8nio/runners:2.45.6`) for Code nodes, hardened containers (read-only, no capabilities).
- `setup/setup.mjs` runs once in the n8n image: creates the credentials from Docker secrets,
  fills the Settings nodes from environment variables, imports and publishes the workflows.
- Workflow JSON is generated by `scripts/build_workflows.py` from one definition plus the Code
  node sources in `src/code/`; CI fails if the committed JSON is stale.

## Test harness

- `tests/events/*.jsonl`: recorded synthetic events (no real people or companies), each with
  its delivery plan (copies, concurrency, auth), scripted sink failures, the approval or reply
  action and the expected result.
- `mocks/mock_sinks.py`: one stdlib HTTP service standing in for chat, social, spreadsheet and
  CRM APIs. Checks the bearer token, records every call, can be scripted to fail per key.
- `tests/harness/run.sh`: fresh disposable stack on an internal Docker network with throw-away
  secrets, replays all events, checks sinks, Mailpit, the ledger and n8n's own execution
  status, writes `out/harness-report.json`, removes everything.
- Measured per run: number of recorded events and HTTP deliveries, duplicate-run results
  (copies sent vs. writes made), and the time from the start of the import on an empty
  database to the first successful execution (split into import, n8n ready, first run).

## Phases (one commit each)

0. Plan, repository skeleton.
1. Code nodes, build script, generated workflows, Code node unit tests.
2. Mock sinks, setup script, disposable stack, recorded events, replay harness.
3. Harness runs on a lab host, fixes found by them, measured results committed.
4. CI: lint, export check, unit tests, the full harness on every push.
5. README with results and screenshots, docs, cover and portfolio text.

## Rules

- Mock sinks only: no real social, email, sheet or CRM accounts.
- No secrets in the repo; harness secrets are generated per run.
- Only measured numbers; a failed check is reported as failed.
